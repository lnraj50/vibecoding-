02. Technical Constraints Guide: Stack, State & Security

When feeding prompts to AI tools, vague instructions cause architecture bloat and hallucinations. Explicit technical constraints force the model to write modular, production-ready code.

1. Stack: Next.js 15 App Router vs. Vite React + Supabase + Tailwind + shadcn

Next.js 15 (App Router)

When to choose: SEO-driven applications, public e-commerce, content platforms, dynamic OpenGraph cards, and integrated Server Actions.

  • Server Components (RSC): Render data-heavy views on the server; zero bundle impact on the client.
  • Streaming & Suspense: Instant initial paint with progressive loading skeletons.
  • Route Handlers: Built-in REST/webhook endpoints without maintaining an external Node server.

Vite React + Supabase (SPA Architecture)

When to choose: Interactive SaaS dashboards, internal tools, real-time collaboration apps, and rapid Lovable prototypes.

  • Sub-second HMR: Near-instant feedback loop while live prompting.
  • Direct-to-Supabase: Client communicates directly with Postgres via auto-generated PostgREST APIs protected by RLS.
  • PWA & Static Hosting: Deployable to any CDN edge (Cloudflare Pages, Vercel) with negligible compute cost.

Tailwind CSS + shadcn/ui: The AI-Native UI Standard

Why AI tools excel with this pairing: shadcn/ui is not an opaque NPM library; it places copy-paste Radix UI primitives directly inside your components/ui folder. AI models can inspect the exact component JSX, style it with utility-first Tailwind classes, and ensure WCAG-compliant keyboard accessibility without CSS collisions.

2. State & Data: TanStack Query, Server Actions & Optimistic UI

TanStack Query (React Query)

Server State Management: Replaces manual useEffect data fetching. Provides automated caching, background refetching on window focus, pagination, query deduplication, and stale-while-revalidate cycles.

Server Actions

RPC Mutation Pattern: Functions that run exclusively on the server but are invoked directly from client forms or buttons. Eliminates manual API boilerplate, handles CSRF tokens, and integrates with server-side validation.

Optimistic UI Updates

Instant UX Feedback: Updates the client interface immediately before the network request finishes. If the server transaction succeeds, data silently synchronizes; if it fails, TanStack Query or React useOptimistic rolls back the UI state cleanly.

3. Security & Validation: Zod Schemas, RLS Rules & Rate Limits

Zod Schemas

Boundary Validation: TypeScript types disappear at runtime. Zod validates untrusted external inputs (API payloads, query strings, user forms) at runtime and automatically infers static TS types to prevent injection and shape mismatch.

Row Level Security (RLS)

Database-Level Isolation: Supabase/Postgres policies that evaluate at the row level using the authenticated user's JWT (auth.uid()). Ensures that even if your frontend code is compromised or manipulated, unauthorized database access is blocked by the engine.

Rate Limiting & Abuse Defense

DDoS & Cost Protection: Sliding-window rate limiters (Upstash Redis or Edge token buckets) applied to public mutations, AI completions, and authentication attempts to prevent automated exhaustion attacks.

03. Vibe Coding Best Practices

1. Atomic Git Commits per Prompt

Never run a prompt on a dirty git tree. Commit before every AI block. When a model hallucinates, run git reset --hard instead of trying to prompt your way out of broken code.

2. Context Window Discipline

Feeding an entire repository degrades model attention. Provide only relevant schema files, type definitions, and the specific component being edited.

3. Contracts First (Types & Schemas)

Define database tables and TypeScript interfaces before prompting for UI. Strong types act as self-correcting rails for the AI generation engine.

4. Tight Verification Feedback Loops

Run TypeScript compilation (tsc --noEmit) or unit tests immediately after each prompt output to catch syntax regressions early.

04. The 5-Phase Vibe Coding Delivery Plan

  • Phase 1: Architecture & Data Modeling: Define database tables, RLS expectations, Zod schemas, and core TypeScript contracts.
  • Phase 2: Scaffolding & Routing: Generate navigation layouts, authentication shells, theme configuration, and empty page routes.
  • Phase 3: Vertical Slice Implementation: Build one complete feature end-to-end (Database → Query/Action → UI Form → Optimistic Response) before moving to the next.
  • Phase 4: Security & Edge Case Hardening: Enforce RLS policies, webhook HMAC verification, loading skeletons, and error boundaries.
  • Phase 5: Performance & Deployment: Run lighthouse audits, verify production builds, configure metadata/SEO, and configure monitoring alerts.

  • Use /compact to reset context window between disparate tasks.
  • Direct Claude Code to run automated tests to self-heal failed builds.

Windsurf & Antigravity

  • Persist project conventions using Cascade Memories.
  • Verify workspace indexing status before triggering complex cross-file workflows.
  • Review proposed shell commands before authorizing execution.

Claude Desktop (MCP)

  • Mount MCP servers (Postgres, GitHub, local directory, Playwright).
  • Inspect live database table schemas via MCP instead of pasting SQL dumps.
  • Prototype UI components inside Artifacts before moving to the repo.

07. Security & Verification Checklist

  • Row Level Security (RLS): Verify RLS is enabled on every Supabase table. Ensure write policies explicitly check auth.uid() = user_id and never fall back to USING (true).
  • Webhook Signatures: Always verify webhook cryptographic signatures (Stripe, Razorpay, Paddle) on raw request bytes before writing orders or credits.
  • API Authentication: Validate session tokens on server actions and route handlers; never trust a client-supplied user ID in request bodies.
  • Secret Storage: Ensure secret keys (Stripe secret, service role keys) exist strictly in server-side environment variables and are never bundled into client JS.
  • Payload Sanitization: Pass all user input through Zod schemas before database persistence to prevent malformed or malicious payloads.

01. Event QR check-in and sales routing

Business outcome

A booth host scans an attendee badge, confirms the person, records a demo interest, and routes the follow-up to a sales rep.

Real-world scenario

Host scans registration EVT-2048 twice during a weak Wi-Fi connection. Both attempts must produce one check-in, with a clear pending or confirmed state.

Minimum data model

Attendee, Event, CampaignMembership, DemoInterest, RepAssignment, CheckInAttempt

End-to-end workflow

Scan → validate identifier → search approved registration data → use approved provider lookup if unmatched → manual search → confirm → persist check-in → enqueue CRM update.

Architecture decisions

Keep registration matching on the server. A repeated request carries the same idempotency key. Queue CRM work separately and display sync status. Enforce booth/event access on every lookup.

Ready-to-use implementation prompt

Build a mobile-first event check-in vertical slice. Use synthetic attendees and a mocked registration adapter first. Add camera permission denied and manual-search paths. Show matching candidates for host confirmation; never silently choose an ambiguous person. Store one check-in per event and attendee using a database uniqueness constraint. Record demo interests separately. Use configured rep routing with an explicit unassigned queue. Add pending, confirmed, retrying, and failed sync states. Keep external credentials on the server.

Acceptance checks

  • Scan twice: one check-in
  • Deny camera: manual search works
  • Provider timeout: recover without losing entry
  • Ambiguous match: require selection
  • Unauthorized host: no attendee data.

What to measure

Duplicate check-ins; scan-to-confirm time; unassigned follow-ups; sync failure rate. These are suggested measures, not promised improvements.

02. Website enquiry to CRM and marketing automation

Business outcome

A visitor requests a trial or downloads content; the website validates the submission and sends only approved fields to CRM and the marketing platform.

Real-world scenario

A trial form is submitted twice; CRM is temporarily unavailable. The visitor receives a truthful receipt while the job retries safely.

Minimum data model

Submission, ConsentEvidence, CampaignAttribution, IntegrationJob, ExternalRecordMapping

End-to-end workflow

Submit → server validation → durable receipt → queue → deduplicate according to business rules → CRM upsert → marketing platform update → job status.

Architecture decisions

Separate enquiry processing from marketing permission. Keep consent timestamp, wording version and source. Validate attribution against allowed fields. Define whether repeated submissions create activities rather than duplicate people.

Ready-to-use implementation prompt

Build an enquiry intake feature with a mock CRM adapter and marketing adapter. Capture name, company, email, enquiry type, campaign source and optional marketing opt-in. Persist the request before acknowledging receipt. Use a submission idempotency key; preserve legitimate later enquiries as distinct activities. Show received rather than synced until integrations confirm success. Add retry limits and an operations queue. Never put integration secrets in browser code.

Acceptance checks

  • Double-click: one request
  • CRM down: durable queued job
  • Opt-in unchecked: no marketing subscription
  • Invalid email: useful field error
  • CRM partial success: retry remaining step without duplication.

What to measure

Receipt-to-sync time; rejected submissions; duplicate rate; integration backlog. These are suggested measures, not promised improvements.

03. Campaign analytics and ROI calculator

Business outcome

A campaign manager compares spend, qualified pipeline and attributed revenue using explicit definitions.

Real-world scenario

Campaign cost is 10,000 and attributed revenue is 30,000. Revenue-based ROI is 200%; this is not a profit-based calculation.

Minimum data model

Campaign, CostItem, Opportunity, AttributionRule, RevenueSnapshot

End-to-end workflow

Load approved sample data → select date range → select attribution rule → calculate → display assumptions → export summary.

Architecture decisions

Use one reporting currency or an explicit FX conversion rule. Keep pipeline separate from won revenue. Prevent division by zero. State the time window and avoid double-counting shared opportunity revenue.

Ready-to-use implementation prompt

Build a campaign ROI dashboard from synthetic JSON. Calculate revenue-based ROI as (attributed revenue minus campaign cost) / campaign cost × 100. Show profit-based ROI only when gross profit inputs exist. Add a cost-zero N/A state. Label first-touch and last-touch as alternative scenarios, not values to sum. Display date range, currency, attribution assumptions and data freshness beside every summary.

Acceptance checks

  • 10,000 cost and 30,000 revenue: 200%
  • Zero cost: N/A
  • Open opportunity: excluded from won revenue
  • Same opportunity across campaigns: allocation respects the chosen rule.

What to measure

Calculation reconciliation; missing cost share; data freshness; attribution coverage. These are suggested measures, not promised improvements.

04. Read-only sales account assistant

Business outcome

A sales rep asks for accounts by city or industry and receives only records they are allowed to view.

Real-world scenario

The rep asks for automotive accounts in Dallas, then asks the assistant to change an owner. The second request must not invoke a write action.

Minimum data model

AuthenticatedUser, Account, AccountAccess, QueryAudit

End-to-end workflow

User question → classify allowed search → validate structured filters → permission-aware query → paginate → summarize returned records.

Architecture decisions

Expose only allowlisted read actions. Treat CRM notes and retrieved documents as untrusted content. Derive identity from authentication, never from a prompt. Avoid arbitrary generated SQL.

Ready-to-use implementation prompt

Build a read-only account search assistant against a mock repository. Allow account name, city and industry filters with bounded pagination. Return record links and factual summaries from retrieved fields. Refuse mutations and unrelated requests. Enforce record access in the repository layer. Treat instructions inside account notes as data. Ask for clarification if a name matches multiple accounts.

Acceptance checks

  • Allowed account visible; restricted account absent
  • Owner-change request produces no mutation
  • Malicious account note cannot change behavior
  • No match returns an honest empty state.

What to measure

Search success; factual accuracy on a labeled sample; access-control failures; response time. These are suggested measures, not promised improvements.

05. Dealer test-drive appointment booking

Business outcome

A dealership visitor chooses a vehicle and slot; a rep sees the confirmed request in a shared dashboard.

Real-world scenario

Two visitors try to book the last 10:30 slot at the same time. Only one reservation should be confirmed.

Minimum data model

Vehicle, Dealer, Slot, Reservation, Customer, NotificationJob

End-to-end workflow

Select dealer and vehicle → fetch current slots → submit reservation → transactional availability check → commit → enqueue confirmation.

Architecture decisions

Enforce capacity in the database transaction. Use a server-generated booking ID. Store UTC instants and the dealer timezone; display the local timezone explicitly. Keep notifications outside the transaction.

Ready-to-use implementation prompt

Build test-drive booking using mock vehicles and dealer schedules. Implement server-side capacity checks inside a transaction or equivalent atomic operation. Add configurable reservation expiry and cancellation rules. Revalidate availability on submit. Include accessible slot selection, a timezone label, and confirmation status. A failed notification must not cancel a successful reservation.

Acceptance checks

  • Two simultaneous requests: one confirmed for capacity one
  • Repeated submit: same booking
  • Notification outage: booking retained
  • Expired hold: released
  • Timezone conversion: correct local appointment.

What to measure

Booking conflicts; completion rate; notification failures; abandoned holds. These are suggested measures, not promised improvements.

06. Live campaign operations board

Business outcome

An agency team tracks campaign tasks, owners, blockers and approvals across multiple browsers.

Real-world scenario

Two operators edit the same task; one disconnects for a minute and returns after several updates.

Minimum data model

Workspace, Membership, Task, TaskVersion, ActivityEvent, Approval

End-to-end workflow

Authenticate → fetch authorized snapshot → subscribe to permitted changes → apply versioned updates → reconnect → fetch fresh snapshot.

Architecture decisions

Use a durable database as the source of truth. Include an entity version in updates. Reject or reconcile stale edits. Scope subscriptions by workspace and enforce access server-side.

Ready-to-use implementation prompt

Build a live campaign board with mocked events first and an adapter for a future authenticated event service. Include task version checks, pending indicators, connection status and a full resync after reconnect. On conflict, show both edits for resolution. Approval must be an explicit authorized action and must create an audit entry.

Acceptance checks

  • Two browsers receive updates
  • Workspace B cannot see A
  • Reconnect fetches missed state
  • Stale edit shows conflict
  • Revoked member loses subscription access.

What to measure

Update lag; reconnect success; edit conflicts; overdue approvals. These are suggested measures, not promised improvements.

07. Newsletter review and controlled delivery

Business outcome

A campaign operator drafts a dealer newsletter, previews personalization and requests approval before scheduling.

Real-world scenario

A CSV contains duplicate emails, unsubscribed contacts and missing first names. The preview must show what each recipient would actually receive.

Minimum data model

AudienceSnapshot, Suppression, TemplateVersion, Approval, DeliveryJob

End-to-end workflow

Import sample audience → normalize → suppress → preview → approve immutable content and audience version → queue authorized delivery.

Architecture decisions

Use synthetic contacts for development. Suppression is checked again at send time. Separate draft, approved and scheduled states. Send through a server-side provider adapter with bounded throughput.

Ready-to-use implementation prompt

Build a newsletter preparation tool with a mock delivery provider only. Normalize duplicate emails, apply suppressions, show fallback personalization and preview mobile layout. Approval must reference exact template and audience versions; changes invalidate approval. Provide dry-run counts and per-recipient validation reasons. Never implement real sending without configured provider credentials and an explicitly authorized production workflow.

Acceptance checks

  • Unsubscribed record excluded
  • Missing name uses approved fallback
  • Edit after approval requires review again
  • Retry does not resend successful deliveries
  • Dry run sends zero messages.

What to measure

Suppression accuracy; invalid record count; approval turnaround; delivery reconciliation. These are suggested measures, not promised improvements.

08. AI-assisted lead data quality review

Business outcome

A marketing operations analyst reviews duplicate candidates and missing fields before any CRM changes.

Real-world scenario

Two leads share a company and surname but have different email addresses. The tool flags a possible match rather than merging them.

Minimum data model

LeadSnapshot, RuleFinding, DuplicateCandidate, ReviewDecision, ChangeProposal

End-to-end workflow

Import synthetic sample → deterministic validation → candidate matching → explain findings → human review → export proposed changes.

Architecture decisions

Distinguish factual validation from AI inference. Preserve original values. Do not invent phone numbers or email addresses. Keep any later update process separate, permissioned and auditable.

Ready-to-use implementation prompt

Build a lead data quality review screen from a synthetic CSV. Flag missing fields and malformed values using deterministic rules. Group possible duplicates with reasons and confidence labels; never auto-merge. AI may suggest standardized company names but must label suggestions. Support accept, reject and needs-review decisions. Export proposals with source record IDs and original values for reconciliation.

Acceptance checks

  • Similar names remain separate without evidence
  • Missing email stays missing
  • Original values preserved
  • Reimport same snapshot does not duplicate findings
  • Export contains only reviewed proposals.

What to measure

Finding precision on reviewed samples; reviewer time; unresolved cases; accepted proposal rate. These are suggested measures, not promised improvements.

13. Clarifications to Read Alongside the Original Guide
The original wording remains above. Apply these qualifications when using it in a real project.
  • Generated code needs review: an explicit prompt improves direction but does not guarantee production readiness, correctness or accessibility.
  • Preserve work before recovery: the original reset suggestion is destructive. Inspect the diff and preserve unrelated or uncommitted work; prefer a focused reversal or a revert of a known commit.
  • Validation is one layer: schema validation checks shape and constraints. Parameterized queries, contextual output escaping, authorization and safe rendering address different threats.
  • Server Actions: treat every callable mutation as an untrusted entry point. Authenticate, authorize and validate inside the action. Framework transport protections do not replace business permission checks.
  • Optimistic UI: rollback is not universally automatic. Implement failure recovery, reconciliation and concurrent-edit behavior for the chosen state library.
  • RLS policies: define policies by operation and role. Check both access to existing rows and validity of proposed rows; test cross-tenant reads and writes. Elevated service credentials can bypass ordinary isolation and must remain server-side.
  • Accessibility: a component library provides a starting point. Labels, keyboard flow, contrast, focus restoration and screen-reader feedback still need verification.
  • Rendering and performance: Server Components can reduce shipped client code, but client dependencies still contribute to bundle size. Streaming, fast refresh and hosting costs depend on implementation and deployment.
  • Versioned examples: named framework versions, tool modes, configuration files and product capability descriptions in the original are retained historical examples, not a verified current compatibility matrix. Check the selected product’s official documentation and repository versions before adopting them.
  • Runtime selection: install commands and scripts should be reviewed before execution; use the runtime version supported by the actual project and its dependency lockfile.



14. Vibe Coding in Simple Technical English
Vibe coding means describing what you want to an AI coding tool, reviewing what it creates, and improving it through small verified steps. You still decide the business rules and check the result. The AI can help write code, explain code, prepare changes and investigate failures.
Example: instead of “Build a lead app,” say “Build a form that receives a trial enquiry, saves it once, assigns a rep using this mapping, and shows whether CRM synchronization is still pending.” This gives the tool a task it can implement and you can verify.
Describe
Explain the user, task, input, business rule and expected result using one small example.
Build
Ask for one complete feature using fake data and the project’s existing tools.
Check
Try success, wrong input, duplicate actions, lack of permission and system failure.
A practical sequence for any area
  1. Show the AI the relevant files and explain the current behavior.
  2. Give one example of the required behavior and the rules that must remain true.
  3. Ask it to identify missing information and explain the affected files.
  4. Have it implement the smallest complete change in a development environment.
  5. Review the change and check the result with realistic synthetic examples.
  6. Fix specific failures, then prepare the tested version for the agreed release process.

01. Database design and safe changes
What does it mean?
A database is the organized storage behind your app. A table stores one kind of thing; a row is one record; a key connects records.
Simple use case
Your agency needs to store clients, campaigns and campaign tasks without repeating client details in every task.
What should you give the AI?
Sample client and campaign records; required fields; who owns each record; duplicate rules.
How to vibe code this area
  1. List the things to store and how they connect.
  2. Define required fields and uniqueness rules.
  3. Create a versioned migration: a recorded change to the database structure.
  4. Load fake records in a development database.
  5. Check reads, writes and relationships; rehearse backup restoration before a risky production change.
Copy-ready build prompt
Design Client, Campaign and Task tables for an agency. Each campaign belongs to one client; each task belongs to one campaign. Use stable IDs, foreign keys and required fields. Inspect the existing schema first. Provide a non-destructive migration and explain every change in simple English. Preserve existing records; do not drop tables or columns. Define a safe approach for adding a required field to an existing populated table. Add fake sample records and queries for campaigns by client. Explain any index with the query it supports. Include tenant isolation and a migration recovery plan.
Copy-ready review prompt
Review the database design and safe changes change against the stated business rule and existing project conventions. Trace one successful example and each listed failure case. Identify assumptions, incomplete integrations and any change that risks existing behavior. Make focused fixes and report checks actually performed. Explain the result to a basic JavaScript developer in simple technical English.
How do you know it works?
  • A task cannot reference a missing campaign.
  • A duplicate business identifier is rejected according to the agreed rule.
  • Existing records survive the migration.
  • One client cannot read another client’s restricted data.
Common mistake
Asking AI to “fix the database” without showing the current schema, sample records or preservation rules.


02. Programming and business logic
What does it mean?
Programming turns a business rule into repeatable steps. A function takes inputs and returns a result or performs an action.
Simple use case
Route a new enquiry to the correct rep based on region and product interest.
What should you give the AI?
Region codes; product codes; active rep mapping; fallback queue; examples of expected assignments.
How to vibe code this area
  1. Write the rule as a small decision table.
  2. Agree what happens when data is missing.
  3. Build a pure routing function before connecting CRM.
  4. Test sample inputs.
  5. Connect the result to the CRM adapter and audit the decision.

01. Blocking and non-blocking operations
Computing basics
In simple technical English
A blocking operation holds up its execution thread while waiting. Non-blocking I/O allows the runtime to handle other work during the wait. In JavaScript, awaiting asynchronous I/O can yield control; heavy synchronous calculation still blocks its event loop.
Real-life business use case
One report endpoint reads a large file synchronously, delaying unrelated website enquiries handled by the same event loop.
What is the trade-off?
Async control flow needs deliberate error handling. Adding async to a function does not automatically move CPU work off the main thread.
How to approach the work
  1. Show the relevant code, current behavior and a synthetic example of the business flow.
  2. Ask the AI to explain whether this concept applies and what evidence is missing.
  3. Use the topic-specific prompt below to make or evaluate one focused change.
  4. Check the business result and the failure condition before using the design more widely.
Copy-ready vibe-coding prompt

01. Ecommerce: catalogue, cart and checkout

Copy-ready build prompt
